# FlashInfer-Bench: Building the Virtuous Cycle for AI-driven LLM Systems

## 1. Paper identity and scope

- This analysis covers arXiv `2601.00227v1`, a preprint by authors from the University of Washington, Carnegie Mellon University, NVIDIA, UC Berkeley and independent researchers. [Title; author footnote](../pdfs/25-flashinfer-bench.md)
- The stated research question is practical: "how can AI-generated kernels be effectively incorporated into production LLM systems?" The work is a benchmark plus an operational workflow, not a new generation model or agent method. [§1](../pdfs/25-flashinfer-bench.md)
- The authors name three gaps: communicating kernel characteristics (ragged distributions, data precision) to agents, tracking kernel performance on real serving traffic instead of uniform or random inputs, and the engineering gap between a promising kernel and an end-to-end system. [§1](../pdfs/25-flashinfer-bench.md)
- The four claimed contributions are the FlashInfer Trace schema (§3.1), the FlashInfer-Bench Dataset (§3.2), an operational workflow that benchmarks generated kernels and applies them in a production system (§3.3–3.5), and an analysis of LLM-generated kernels on LLM-serving workloads (§4). [§1, contribution list; Figure 1](../pdfs/25-flashinfer-bench.md)
- The empirical study covers four frontier models writing CUDA and Triton kernels in a feedback loop, measured on one NVIDIA B200 GPU, plus one end-to-end serving case study on a single kernel definition. [§4.1–4.2; §4.5](../pdfs/25-flashinfer-bench.md)
- Correctness in this work means sampled, tolerance-based agreement with a PyTorch reference function on dataset workloads. Nothing is formally verified, and no proof of equivalence is claimed. [§3.1; §3.3](../pdfs/25-flashinfer-bench.md)
- Out of scope by the authors' own statement: multi-GPU and communication kernels, and a wider range of models, hardware devices and programming languages. [§6, Limitations and next steps](../pdfs/25-flashinfer-bench.md)
- The text describes a public leaderboard and periodically frozen, versioned dataset snapshots, but gives no snapshot identifier, dataset version or URL for the results it analyses. [§3.4](../pdfs/25-flashinfer-bench.md)

## 2. Concepts and terminology

### The Trace schema and its four components

- FlashInfer Trace is a self-contained JSON schema covering the kernel task, workloads, the solution and the evaluation result. It is meant to be readable by humans and agents, minimal (no implementation-related system metadata in a Definition) yet sufficient (each operator introduces the axes and constraints it needs). [§1; §3.1](../pdfs/25-flashinfer-bench.md)
- **Definition** is a JSON specification of the operator's input/output tensors and dtypes, its dimension axes, and "a plain PyTorch-based reference function run as the single source of mathematical semantics"; optional constraints encode relations among axes. Figure 2 (image inspected) lists its fields as `name`, `op_type`, `axes`, `inputs`, `outputs`, `reference`, and optional `tags`, `description`, `constraints`. [§3.1, Definition; Figure 2](../pdfs/25-flashinfer-bench.md)
- Each axis is either `const` (a value fixed at compile time) or `var` (a value determined by the workload); the authors present this as what lets an agent specialize a kernel for specific shapes. [§3.1](../pdfs/25-flashinfer-bench.md)
- Semantics are carried by executable code, not prose: in the GEMM example `gemm_n128_k2048` the `reference` field is the source text of `run(A, B)` returning `torch.matmul(A, B.T)`, with `M` variable, `N = 128` and `K = 2048` constant, and all tensors `float16`. [Appendix A.1](../pdfs/25-flashinfer-bench.md)
- The paged GQA decode example has eight axes (four `const`: `num_qo_heads = 32`, `num_kv_heads = 4`, `head_dim = 128`, `page_size = 1`; four `var`), two string constraints (`len_indptr == batch_size + 1`, `num_kv_indices == kv_indptr[-1].item()`), `bfloat16` tensors, `int32` index arrays, and a `float32` scalar `sm_scale` with shape `null`. [Appendix A.2](../pdfs/25-flashinfer-bench.md)
- That example's reference is a Python-loop PyTorch function that asserts the constant axes and constraints, converts to `float32`, computes per-head softmax attention and a base-2 log-sum-exp, and casts the output to `bfloat16`. The reference therefore also fixes intermediate precision and empty-sequence behaviour (zero output, `-inf` LSE). [Appendix A.2](../pdfs/25-flashinfer-bench.md)
- Ragged inputs are expressed by passing both the full page-table tensor and an integer index-pointer tensor as inputs, so variable-length sequences are ordinary tensors plus constraints. [§3.1](../pdfs/25-flashinfer-bench.md)
- **Workload** is "a concrete test input bound to a particular kernel Definition": every `var` axis receives an integer value, and each input is materialized as a recorded safetensors dump, a random tensor, or a literal scalar. Its fields are `uuid`, `axes`, `inputs`. [§3.1, Workload; Figure 2](../pdfs/25-flashinfer-bench.md)
- The GQA workload example mixes all three kinds: `q`, `k_cache`, `v_cache` are `random`, `kv_indptr` and `kv_indices` come from a safetensors file by key, and `sm_scale` is the scalar `0.0883883461356163`. [Appendix A.2](../pdfs/25-flashinfer-bench.md)
- **Solution** is a concrete implementation satisfying a chosen Definition's interface and semantics. The examples carry `name`, `definition`, `author`, `spec` (`language`, `target_hardware`, `entry_point` such as `main.py::run`, `dependencies`), `sources` (path and content) and `description`. [§3.1, Solution; Appendix A.1](../pdfs/25-flashinfer-bench.md)
- **Evaluation** is "an immutable benchmarking record" binding one Definition × Solution × Workload. The examples contain `status` (for example `PASSED`), `environment` (`hardware`, `libs`), `timestamp`, `log`, `correctness` (`max_relative_error`, `max_absolute_error`, `extra`) and `performance` (`latency_ms`, `reference_latency_ms`, `speedup_factor`). [§3.1, Evaluation; Appendix A.1; Figure 2](../pdfs/25-flashinfer-bench.md)
- A trace record's top-level keys are `definition`, `workload`, `solution` and `evaluation`; a bare workload is the same record with `solution` and `evaluation` set to `null`. [Appendix A.1](../pdfs/25-flashinfer-bench.md)

### Definition identity and specificity

- Two kernel invocations fall under the same Definition if and only if they share the same I/O spec and reference semantics, expose the same axes with identical `const`/`var` roles, and agree on all `const`-axis values. [§3.2](../pdfs/25-flashinfer-bench.md)
- The authors prefer specific Definitions over permissive ones, "ideally down to a specific model layer kernel call". Optional inputs and behavioural flags are disallowed, default behaviour is encoded inside the reference, and divergent behaviour requires a new Definition. [§3.2](../pdfs/25-flashinfer-bench.md)

### Correctness criteria

- Deterministic kernels (GEMM, normalization, attention) are compared elementwise to the reference output; an output is correct if every element satisfies \(|y_{\text{sol}}-y_{\text{ref}}|\leq\epsilon_{\text{abs}}+\epsilon_{\text{rel}}\cdot|y_{\text{ref}}|\). [§3.3, Deterministic Kernels; Eq. 1](../pdfs/25-flashinfer-bench.md)
- Any output containing NaN or Inf is rejected, and the maximum observed error across all tested elements and trials is recorded per kernel. [§3.3, Deterministic Kernels](../pdfs/25-flashinfer-bench.md)
- Low-precision kernels (for example FP8) use a matched-ratio rule in place of a looser global tolerance: the kernel is correct if at least a fraction \(\rho\) of output elements meets the standard criterion. \(\rho = 0.95\) is given only as an example. [§3.3, Low-Precision Kernels](../pdfs/25-flashinfer-bench.md)
- Stochastic kernels (sampling) are checked distributionally: the expected distribution is derived from the input probabilities and an optional top-k or top-p mask, the kernel is executed repeatedly to obtain an empirical distribution, and the total variation distance must be below a threshold \(\tau_{\text{TVD}}\). [§3.3, Stochastic Kernels](../pdfs/25-flashinfer-bench.md)
- Sampling also has a hard support check: any sample outside the mask, such as an index that top-k should exclude, is an immediate failure. [§3.3, Stochastic Kernels](../pdfs/25-flashinfer-bench.md)
- The source gives the form of each criterion but no numeric value for \(\epsilon_{\text{abs}}\), \(\epsilon_{\text{rel}}\), \(\tau_{\text{TVD}}\), the \(\rho\) actually used, or the number of sampling repetitions. [§3.3](../pdfs/25-flashinfer-bench.md)

### Timing, isolation and scheduling

- Timing runs only after acquiring a per-GPU, multiprocess-visible device lock; each kernel performs \(w\) untimed warm-up runs and \(m\) timed runs, uses CUDA-event device-side timing, and reports the mean latency over the \(m\) runs. The values of \(w\) and \(m\) are not stated. [§3.3, Performance Measurement](../pdfs/25-flashinfer-bench.md)
- Isolated mode runs each solution in its own subprocess, terminates it on completion or timeout, and tears down the CUDA context; the stated threat is an LLM "hacking" the benchmark, for example by reading residual memory to infer reference outputs. [§3.3, Isolation](../pdfs/25-flashinfer-bench.md)
- Persistent mode keeps one long-lived worker per GPU plus pre-warmed spares to cut start-up cost. Execution defaults to persistent mode, and only solutions that repeatedly fail are deferred to isolated runs. [§3.3, Isolation; System Support](../pdfs/25-flashinfer-bench.md)
- A scheduler assigns Solution × Workload jobs to device workers in micro-batches using the Hungarian algorithm over a cost matrix updated by an exponentially weighted moving average; inputs, reference outputs and compiled solutions are cached and reused. [§3.3, System Support](../pdfs/25-flashinfer-bench.md)

### Metrics

- \(\text{fast}_p\) is adopted from KernelBench: \(\text{fast}_p=\frac{1}{N}\sum_{i=1}^{N}\mathbf{1}(\text{correct}_i\land\{\text{speedup}_i>p\})\), the proportion of workloads on which a solution is both correct and more than \(p\) times as fast as the baseline. [§4.2, Metrics; Eq. 2](../pdfs/25-flashinfer-bench.md)
- \(\text{fast}_0\) is the correctness rate; varying \(p\) gives a curve whose area is described as overall performance; a model's curve is the average of \(\text{fast}_p\) over all of its generated solutions. [§4.2, Metrics](../pdfs/25-flashinfer-bench.md)
- The comparison baseline is the FlashInfer library kernel; when no FlashInfer kernel exists (the example given is bf16 GEMM) PyTorch is used. A speedup threshold therefore refers to different baselines for different kernel types. [§4.2, Metrics](../pdfs/25-flashinfer-bench.md)
- In both example Evaluation records the stored `speedup_factor` equals `reference_latency_ms / latency_ms` (checked arithmetically). In the GQA example 29.44 ms over 0.0227 ms gives 1299×, which reads as a ratio to the unoptimized PyTorch reference loop, not to FlashInfer; the source does not define the field. [Appendix A.1; Appendix A.2](../pdfs/25-flashinfer-bench.md)

### apply() dynamic substitution

- `flashinfer_bench.apply()` is a runtime dispatcher that maps a kernel call to the best-performing validated Solution in a local dataset and otherwise falls back to the original implementation. [§3.5; Figure 5](../pdfs/25-flashinfer-bench.md)
- A decorator API wraps an operator, whose body becomes the fallback, and takes a fixed Definition name or a resolver that builds the name from runtime arguments (Figure 5 shows `gemm_n{B.shape[0]}_k{B.shape[1]}`); an imperative API serves arbitrary call sites. FlashInfer operators are routed without code changes by setting `FIB_ENABLE_APPLY=1`. [§3.5, Interface and Usage; Figure 5](../pdfs/25-flashinfer-bench.md)
- Before the engine starts, the runtime builds an index from the local dataset: it filters traces by a configurable error threshold, forms a key from workload features such as shapes, and stores the fastest solution per key. The most frequently chosen solutions are compiled ahead of time at a configurable ratio and the rest just in time. [§3.5, Offline Cache Prebuilding](../pdfs/25-flashinfer-bench.md)
- Online dispatch constructs the key from the call's arguments, performs an \(O(1)\) index lookup, and finds or compiles a kernel; the authors call the overhead negligible when CUDA graph is enabled and warm-up is done. [§3.5, Online Lightweight Dispatch](../pdfs/25-flashinfer-bench.md)

## 3. Methodology and experimental setup

### Dataset construction

- Workloads are collected by serving DeepSeek-V3, Llama-3.1-8B and Qwen3-30B-A3B in SGLang with default, commonly used configurations (for example native FP8 quantization and tensor-parallel size 8 for DeepSeek-V3) against ShareGPT prompts. [§3.2](../pdfs/25-flashinfer-bench.md)
- Full tensors are dumped when input values materially affect performance (sampling probability distributions) or correctness (extreme edge cases); otherwise seeded random runtime tensors are used to save storage. [§3.2](../pdfs/25-flashinfer-bench.md)
- Workloads are deduplicated along performance-sensitive axes (batch size) and tensor statistics (average sequence length for attention); the text says each Definition keeps about 50 workloads. [§3.2](../pdfs/25-flashinfer-bench.md)
- The dataset contains eight kernel types: GEMM, ragged and paged GQA, ragged and paged MLA, fused MoE, RMS normalization and sampling, including fused, non-deterministic and low-bit (FP8 GEMM) kernels. [§4.1](../pdfs/25-flashinfer-bench.md)
- Each unique combination of fixed dimensions is a separate definition, giving 41 kernel definitions; the workload set is 1,600 workloads after shape-based deduplication and filtering. [§4.1](../pdfs/25-flashinfer-bench.md)
- Solutions come from four models (Gemini 2.5 Pro, Claude Opus 4.1, GPT-5 and OpenAI o3) in two languages (CUDA and Triton); 240 solutions were evaluated, producing 9,600 evaluation results. CUTLASS and CuTe DSL are said to be supported, with no results reported. [§4.1](../pdfs/25-flashinfer-bench.md)

### Agent, prompts and hardware

- All models run inside the same feedback-loop agent: initialize from Definition, Language and Hardware, generate a solution, benchmark it with FlashInfer-Bench, keep it if the trace status is `PASSED`, and ask the agent to optimize from the trace, for \(N\) iterations. [§4.2, Setup; Algorithm 1](../pdfs/25-flashinfer-bench.md)
- The final solution is the passed candidate with the highest trace speedup across all iterations. The iteration limit \(N\) (the "improvement limit") is not given a value. [§4.2, Setup; Algorithm 1](../pdfs/25-flashinfer-bench.md)
- Kernel performance is measured on an NVIDIA B200 GPU; the example Evaluation records list `torch 2.8.0+cu128`, `triton 3.4.0` and `cuda 12.8`. [§4.2, Setup; Appendix A.1](../pdfs/25-flashinfer-bench.md)
- There is one base prompt and one optimization prompt per language, with placeholders `{target_gpu}`, `{definition}`, `{trace_logs}` and `{current_code}`. The base prompt says the reference code is the mathematical specification but unoptimized; the optimization prompt says to fix compile errors, runtime errors or incorrect outputs first and to optimize only a functionally correct kernel. [Appendix C.1–C.4](../pdfs/25-flashinfer-bench.md)
- CUDA solutions must be returned as exactly three files (`kernel.h`, `kernel.cu`, `main.cpp`) with a `run` entry point exposed through `PYBIND11_MODULE`; Triton solutions must expose `run`, handle device placement themselves, and pass `ast.parse()`. [Appendix C.1; Appendix C.3](../pdfs/25-flashinfer-bench.md)
- The CUDA optimization prompt includes the line "Consider using specialized libraries if beneficial"; the CUDA base prompt has no such line. [Appendix C.3; Appendix C.4](../pdfs/25-flashinfer-bench.md)
- The authors state that hardware information, "including specifications and relevant documentation", was provided to the models; the prompt listings show only the `{target_gpu}` placeholder. [§4.3; Appendix C](../pdfs/25-flashinfer-bench.md)

### Leaderboard and end-to-end setup

- The public leaderboard accepts submissions in Trace format and reports kernel- and device-stratified correctness, \(\text{fast}_p\) curves, per-workload latency and end-to-end latency deltas. Its stated anti-reward-hacking defences are runtime isolation, hidden workloads and the dedicated validators; which or how many workloads are hidden is not stated. [§3.4](../pdfs/25-flashinfer-bench.md)
- The end-to-end study uses the fused add RMSNorm kernel with hidden size 4096 (`fused_add_rmsnorm_h4096`) in SGLang serving Llama-3.1-8B-Instruct, at batch sizes/concurrency levels 1, 16 and 64. [§4.5, Experimental Setup; Figure 8](../pdfs/25-flashinfer-bench.md)
- Four configurations are compared: Original (native SGLang with the FlashInfer backend), Fallback Substitution (the FlashInfer kernel routed through apply()), a Gemini-2.5-Pro Triton kernel and a GPT-5 Triton kernel, the last two generated by the agent and validated by FlashInfer-Bench. The text and the figure legend disagree on whether apply() is enabled in Original; see section 6. [§4.5, Experimental Setup; Figure 8](../pdfs/25-flashinfer-bench.md)
- Each end-to-end reading is the mean latency over 4 requests with the same input and output length after a system warm-up. The isolated kernel latencies in the same figure come from benchmark traces, not from the serving run. [§4.5, Experimental Setup](../pdfs/25-flashinfer-bench.md)

[Figure 4](../pdfs/25-flashinfer-bench.md)

### Case studies

- For `gemm_n4096_k4096`, the text reports that GPT-5's Triton kernel is 4.5× faster than its CUDA kernel, with mean execution times of 0.11 ms and 0.5 ms on tested workloads. This compares two generated kernels with each other, not with the baseline. [§4.4, GEMM](../pdfs/25-flashinfer-bench.md)
- The described CUDA kernel uses fixed 128×256×64 block tiles, 8 warps per block and 16 WMMA operations per warp, with no inter-tile prefetching or software pipelining. The Triton kernel autotunes over four tile configurations keyed on `M`, uses compiler pipelining of depth 4 and reaches `tcgen05` through `tl.dot()`; the authors identify the tensor-core primitive as the largest source of the difference. [§4.4, GEMM; Appendix B.1](../pdfs/25-flashinfer-bench.md)
- Appendix B.1 reports that the GPT-5 Triton GEMM kernel is correct on all evaluated workloads, with a speedup against `torch.nn.functional` of 0.2× across all workloads and a best case of 0.6× on one workload. The aggregation behind "across all workloads" is not stated. [Appendix B.1](../pdfs/25-flashinfer-bench.md)
- Appendix B.2 lists a Gemini-2.5-Pro CUDA GEMM solution that calls `cublasGemmEx`; it is correct on all evaluated workloads with a speedup of 0.97× across all workloads and a best case of 1.03× on one workload, against the same PyTorch baseline. [Appendix B.2](../pdfs/25-flashinfer-bench.md)
- For `gqa_paged_decode_h32_kv8_d128_ps1`, an o3 Triton kernel is correct on all evaluated workloads at 0.19× of FlashInfer across all workloads, with a best case of 0.98× on 3 workloads. [Appendix B.3](../pdfs/25-flashinfer-bench.md)
- GPT-5's CUDA kernel for the same definition is correct on all evaluated workloads at 0.02× of FlashInfer across all workloads, best case 1.02× on one workload with batch size 1; it processes one batch element and one KV head per block with scalar FP32 streaming softmax. [§4.4, GQA Paged Decode; Appendix B.4](../pdfs/25-flashinfer-bench.md)
- When GPT-5-2025-08-07 (high reasoning) was explicitly prompted with attention-kernel optimization strategies and CUDA intrinsic instructions, it "failed to generate correct kernels that utilize these optimizations in 10 attempts". [§4.4, GQA Paged Decode](../pdfs/25-flashinfer-bench.md)
- The Appendix A example records show a Claude Opus 4.1 Triton GEMM solution at 0.0230 ms versus a 0.0252 ms reference (1.095×, zero recorded error) on one workload with `M = 6`, and a Claude Opus 4.1 Triton GQA solution passing with maximum relative error 0.0148 and maximum absolute error 0.000488. These are single evaluations that illustrate the record format. [Appendix A.1; Appendix A.2](../pdfs/25-flashinfer-bench.md)

## 5. Authors' conclusions

- The authors conclude that the Trace schema standardizes operator contracts, real serving workloads, candidate implementations and immutable evaluations, and that this closes the loop from generation to production impact. [§6](../pdfs/25-flashinfer-bench.md)
- They state three practical takeaways: compilation is the dominant failure mode; models struggle to exploit hardware features; and language choice is a trade-off in which Triton yields high correctness and usability while CUDA, "when successful", reaches higher peak performance. [§1; §6](../pdfs/25-flashinfer-bench.md)
- They infer that current models lag human-written kernels in most cases, with memory-bound RMSNorm the exception because its speed saturates at memory bandwidth. [§4.3](../pdfs/25-flashinfer-bench.md)
- They read library calls two ways: as evidence that models can use their environment to reach near-human CUDA performance, and as reliance on libraries in place of GPU-programming understanding. They recommend restricting library access during training and allowing it at inference. [§4.3, Agents have learned to call libraries](../pdfs/25-flashinfer-bench.md)
- They argue that DSLs with suitable abstractions let agents apply advanced optimizations by lowering coordination complexity, and that effective CUDA use for complex kernels likely needs reinforcement learning with execution feedback or curated expert-kernel datasets. [§4.4](../pdfs/25-flashinfer-bench.md)
- They conclude that dynamic substitution "adds negligible overhead and reliably converts kernel-level gains into lower latency and higher throughput in LLM serving", and that apply() can substitute the best validated kernel into engines such as SGLang and vLLM with zero code changes. [§6](../pdfs/25-flashinfer-bench.md)

## 6. Limitations and open questions

### Limitations stated by the source

- The scope excludes multi-GPU and communication kernels, and the range of supported models, hardware devices and programming languages "remains limited". [§6, Limitations and next steps](../pdfs/25-flashinfer-bench.md)
- Improving correctness verification "to prevent reward hacking and ensure reliable benchmarking outcomes" is listed as future work, which concedes that the current validators and isolation are not presented as a complete defence. [§6, Limitations and next steps](../pdfs/25-flashinfer-bench.md)
- Generative synthesis is acknowledged to introduce "correctness and security risks without stringent validation". [§2.2, Generative program synthesis](../pdfs/25-flashinfer-bench.md)

### Analyst caveats and missing evidence

- **Unspecified acceptance parameters:** no numeric tolerance, matched ratio in use, TVD threshold, sampling repetition count, warm-up count, timed-run count or agent iteration limit is given, so the pass rates and speedups cannot be reproduced or compared with other benchmarks' gates from the paper alone. [Basis: §3.3; Algorithm 1](../pdfs/25-flashinfer-bench.md)
- **Sampled testing only:** correctness is agreement with the reference within tolerance on roughly 40–50 workloads per definition, many with seeded random tensors; passing says nothing about shapes or values outside the collected distribution. [Basis: §3.2; §3.3; §4.1](../pdfs/25-flashinfer-bench.md)
- **Reference is trusted:** the PyTorch `run` function is the sole source of semantics and no check of the reference against the production kernel it was captured from is described; the `status:verified` tag in the examples is not defined. [Basis: §3.1; Appendix A.1](../pdfs/25-flashinfer-bench.md)
- **Low-precision rule tolerates outliers:** under the matched-ratio rule a fraction \(1-\rho\) of elements may violate the bound by an unbounded amount, apart from the NaN/Inf rejection. [Basis: §3.3, Low-Precision Kernels](../pdfs/25-flashinfer-bench.md)
- **Anti-gaming measures are described, not evaluated:** no experiment shows a detected exploit, the default execution path is the persistent (non-isolated) mode, and hidden workloads are mentioned only for the leaderboard service. [Basis: §3.3, Isolation; System Support; §3.4](../pdfs/25-flashinfer-bench.md)
- **Selection on the measured benchmark:** the agent receives FlashInfer-Bench traces as feedback and the reported solution is the best-speedup passed candidate; the text does not say whether feedback workloads are disjoint from the evaluation workloads. [Basis: §4.2; Algorithm 1](../pdfs/25-flashinfer-bench.md)
- **Library calls count as solutions:** a kernel that delegates to cuBLAS is scored like a hand-written kernel, and the CUDA optimization prompt itself suggests considering specialized libraries, so "learned to call libraries" is partly a prompted behaviour. [Basis: §4.3; Appendix C.4](../pdfs/25-flashinfer-bench.md)
- **Mixed baselines:** \(\text{fast}_p\) uses FlashInfer or PyTorch depending on availability, and the stored `speedup_factor` in the examples is relative to the unoptimized reference; how the leaderboard baseline latency is represented in a trace is not specified. [Basis: §4.2, Metrics; Appendix A.2](../pdfs/25-flashinfer-bench.md)
- **Timing statistics and hardware:** only mean latency is reported, with no variance, confidence interval or repeat count, at kernel latencies of roughly 0.01–0.03 ms, and all kernel measurements are on one B200. [Basis: §3.3, Performance Measurement; §4.2; Figure 8](../pdfs/25-flashinfer-bench.md)
- **End-to-end claim is one-directional and narrow:** the experiment covers one kernel definition, one engine and one served model, and shows slower generated kernels producing higher request latency. No generated kernel faster than FlashInfer is substituted, throughput is not measured, vLLM is not tested, and the serving GPU and output length are not stated. [Basis: §4.5; Figure 8; §6](../pdfs/25-flashinfer-bench.md)
- **Conclusions stronger than the evidence:** CUDA's "higher peak performance" is argued, not measured (the observation is higher correctness and speed with Triton, and the strong GEMM CUDA curves are attributed to cuBLAS calls); and by the analyst reading of Figure 6 only Gemini 2.5 Pro in Triton exceeds the RMSNorm baseline on a majority (about 0.70) of evaluations. [Basis: §4.3; §6; Figure 6](../pdfs/25-flashinfer-bench.md)

### Source inconsistencies

- **Source inconsistency (case-study kernel):** §4.4 analyses "GPT-5's generated Triton and CUDA kernels" for `gemm_n4096_k4096`, describes the CUDA kernel as a WMMA tiling kernel and points to Appendix B.2 for it, but Appendix B.2 is labelled as generated by Gemini-2.5-Pro and invokes cuBLAS. The WMMA kernel described in §4.4 is not listed. [§4.4; Appendix B.2](../pdfs/25-flashinfer-bench.md)
- **Source inconsistency (GEMM speedups):** §4.4 says the Triton kernel is 4.5× faster than the CUDA kernel (0.11 ms versus 0.5 ms), while the appendix reports 0.2× for the Triton kernel and 0.97× for the listed CUDA kernel against the same PyTorch baseline. The 4.5× value is specific to the §4.4 comparison; the appendix values are specific to the listed kernels. [§4.4; Appendix B.1; Appendix B.2](../pdfs/25-flashinfer-bench.md)
- **Source inconsistency (Gemini kernel speed):** the §4.5 setup calls the Gemini-2.5-Pro Triton kernel "a generated kernel faster than the baseline", but Figure 8 and the following paragraph give 0.0160 ms for it against 0.0112 ms for FlashInfer at batch size 64, and it is slower at batch sizes 1 and 16 as well. [§4.5; Figure 8](../pdfs/25-flashinfer-bench.md)
- **Source inconsistency (Original configuration):** the §4.5 text defines Original as native SGLang with the FlashInfer backend "and apply() enabled", whereas the Figure 8 legend reads "Original (Apply Disabled)". The overhead comparison only makes sense under the legend's reading. [§4.5; Figure 8](../pdfs/25-flashinfer-bench.md)
- **Source inconsistency (workload counts):** §3.2 says each Definition keeps about 50 workloads, §4.1 gives 1,600 workloads for 41 definitions (about 39 each, derived), and the Figure 4 screenshot shows n = 660 workloads. The three figures are not reconciled in the source. [§3.2; §4.1; Figure 4](../pdfs/25-flashinfer-bench.md)
- **Unreconciled correctness counts:** the Figure 4 caption pass rates (83.9%, 71.3%, 48.8%), the Figure 7 per-language rates and the "32 correctness errors" have no stated denominators. Derived: the unweighted mean of the eight Figure 7 bars is 68.6%, which over 240 solutions would imply roughly 75 failures, not 32, if the bars were per-solution rates with equal group sizes; the source does not say they are. [Figure 4 caption; Figure 7; §4.1; §4.3](../pdfs/25-flashinfer-bench.md)
- **Source inconsistency (Triton version):** the Triton prompts state "Triton Version: 3.3.1" while the example evaluation environments record `triton 3.4.0`. [Appendix C.1; Appendix A.1](../pdfs/25-flashinfer-bench.md)
- **Minor notation issues:** Figure 2 lists the Solution `spec` field as an array (spelled "arrary") while the appendix examples show an object, and \(N\) denotes the iteration limit in Algorithm 1 but the number of workloads in Eq. 2. [Figure 2; Appendix A.1; Algorithm 1; Eq. 2](../pdfs/25-flashinfer-bench.md)

## 7. Relevance to this project — interpretation

- **Proposal:** shape the Stage 1 input schema after the Definition record: named axes with an explicit `const`/`var` role, input and output tensors with dtype and symbolic shape, constraint expressions, and an executable reference. Ask a clarification question whenever a `const`/`var` role or a constant value cannot be determined from the user's context. [Basis: §3.1; Appendix A.2](../pdfs/25-flashinfer-bench.md)
- **Proposal:** forbid optional inputs and behaviour flags in a Stage 1 spec and write one spec per behaviour, with defaults fixed inside the reference, so the natural-language spec, the Lean spec and the oracle share a single contract. [Basis: §3.2](../pdfs/25-flashinfer-bench.md)
- **Proposal:** record in the spec the details a reference fixes implicitly, such as intermediate precision, output cast and empty-input behaviour, since a Lean spec written from prose alone could miss them. [Basis: Appendix A.2](../pdfs/25-flashinfer-bench.md)
- **Proposal:** in Stage 2 store two separately named baselines, the latency of the semantic reference and the latency of the strongest available production or library kernel, and never report a speedup without naming which one it uses. The 1299× example shows how misleading a reference-relative ratio can be. [Basis: §4.2, Metrics; Appendix A.2](../pdfs/25-flashinfer-bench.md)
- **Proposal:** represent every fuzzing or benchmark input as a workload record with axis values and a per-input materialization kind (recorded dump, seeded random, scalar literal), so Stage 3 and Stage 4 inputs are replayable and index-structured inputs satisfy the declared constraints. [Basis: §3.1, Workload; §3.2; Appendix A.2](../pdfs/25-flashinfer-bench.md)
- **Proposal:** choose the correctness validator from the kernel class recorded in the spec (elementwise tolerance, matched ratio for low precision, distributional test plus support check for sampling) and write the numeric thresholds into each evaluation record, which the source omits. [Basis: §3.3](../pdfs/25-flashinfer-bench.md)
- **Proposal:** store kernel-pool entries as immutable solution-plus-evaluation records carrying status, maximum absolute and relative error, latency, baseline latency and an environment snapshot, so a pooled kernel's evidence can be audited later. [Basis: §3.1, Evaluation; Appendix A.1](../pdfs/25-flashinfer-bench.md)
- **Proposal:** add a cheap compile-and-parse gate before fuzzing in Stage 3 and feed compiler logs back to the writer, since compilation dominated the failures reported here. [Basis: §4.3; Appendix C.2](../pdfs/25-flashinfer-bench.md)
- **Proposal:** decide and record a library-call policy per task (for example whether delegating to cuBLAS counts as a kernel), and tag pooled kernels that delegate, so pool statistics are not dominated by wrappers. [Basis: §4.3; Appendix B.2; Appendix C.4](../pdfs/25-flashinfer-bench.md)
- **Proposal:** keep the Stage 4 workloads disjoint from those used for Stage 3 feedback and selection, because picking the best-speedup candidate on the same measurements biases the reported gain. [Basis: Algorithm 1; §3.4](../pdfs/25-flashinfer-bench.md)
- **Proposal:** run the final validation in a fresh subprocess with CUDA-context teardown, use a persistent worker only for inner-loop throughput, and record which mode produced each measurement. [Basis: §3.3, Isolation](../pdfs/25-flashinfer-bench.md)
- **Proposal:** report per-workload-key results (for example per batch size) alongside any aggregate, and consider delivering a shape-keyed selection with a fallback in place of one kernel when winners differ by shape. [Basis: §3.5; Figure 8](../pdfs/25-flashinfer-bench.md)
- **Proposal:** do not assume that supplying hardware documentation makes an agent use newer tensor-core instructions; record which primitive a candidate uses and plan a compiler-backed DSL variant in the batch as an alternative. [Basis: §4.3; §4.4](../pdfs/25-flashinfer-bench.md)
