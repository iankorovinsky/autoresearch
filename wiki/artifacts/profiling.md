# GPU profiling metrics and collection methods

This reference covers NVIDIA CUDA workloads for the kernel research harness. It maps measurements to collection methods across a full GPU, a MIG device, multiple GPUs on one node, and multiple nodes. Availability depends on the exact device, driver, tool version, and job permissions. The [Waterloo provider investigation](compute/uwaterloo-datasci.md) records what worked in live allocations.

## Measurement scope

- **Kernel launch:** Attribute activity to one launch on one CUDA device. Record its kernel name, launch geometry, stream and device, input shape, and launch index or correlation ID.
- **Callable or operation:** Measure a complete invocation, which may enqueue several kernels, copies, synchronization calls, or collectives. Include the streams and ranks on its completion path.
- **Job or device:** Measure scheduler and setup time, board or instance telemetry, topology, and resource usage. Record the sampling interval and whether other workloads could contribute to a reading.

Use separate runs for baseline timing, tracing, and hardware-counter collection. Tracing adds instrumentation. Nsight Compute can replay or serialize launches and change cache or clock conditions. Record the collection settings so the reported time has a reproducible meaning. [CUDA event API](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-runtime-api/group__CUDART__EVENT.html) · [Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)

## Time, throughput, and scheduling

- **Kernel duration, launch count, and duration distribution:** Use Nsight Systems GPU activity timestamps, or CUPTI Activity for programmatic collection. Group by kernel and launch configuration and retain individual samples when investigating variance. A trace can separate GPU execution time from idle gaps between launches. [Nsight Systems guide](https://docs.nvidia.com/nsight-systems/UserGuide/) · [CUPTI Activity API](https://docs.nvidia.com/cupti/api/group__CUPTI__ACTIVITY__API.html)
- **Callable latency and throughput:** Place CUDA Events around work on the measured stream and wait for the stop event before reading it. For multiple streams, join all relevant work into the timed completion path. Record raw samples, warm-up count, cache policy, and event-pair overhead. Report median and a tail percentile with the sample count. Compute throughput as completed items, tokens, or operations divided by elapsed time over the same scope. For very short calls, measure a batch with a documented repetition and synchronization policy. [CUDA event API](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-runtime-api/group__CUDART__EVENT.html)
- **Host wall time, launch overhead, and synchronization:** Use a monotonic host timer with explicit completion boundaries for end-to-end latency. Use Nsight Systems to inspect CUDA API time, launch-to-start delay, CPU dispatch gaps, GPU idle time, stream dependencies, and waits. Record setup, compile/JIT, first invocation, and steady state separately. For cluster jobs, derive queue wait from Slurm submission and start timestamps and report it alongside execution time. [Nsight Systems guide](https://docs.nvidia.com/nsight-systems/UserGuide/) · [Waterloo Slurm guide](https://datasci-gpu.cs.uwaterloo.ca/slurm.html)
- **Per-operator attribution:** Use PyTorch Profiler to correlate framework operators with CUDA activity, shapes, and optional memory events, or use NVTX ranges to label phases in Nsight Systems. Validate that a trace contains actual GPU events before interpreting operator-to-kernel attribution. PyTorch tracing has a provider-specific warm-up example. [PyTorch Profiler](https://docs.pytorch.org/docs/stable/profiler.html) · [Modal profiling investigation](compute/modal.md#why-the-first-pytorch-trace-was-empty)

## Kernel resources and hardware counters

Use the installed version of Nsight Compute to inspect available sections and metric names for the target GPU. Its sections group metrics by question. Query results and section listings alone cannot establish that a job can collect those metrics. [Nsight Compute CLI](https://docs.nvidia.com/nsight-compute/NsightComputeCli/) · [Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)

- **Launch geometry and resource limits:** Capture grid and block dimensions, registers per thread, static and dynamic shared memory per block, local stack, and register spills. Use `ptxas -v` and `cuobjdump --dump-resource-usage` for compiler and binary resources. Use the launch configuration for dynamic shared memory and Nsight Compute `LaunchStats` for launch-level inspection where permitted. Disassemble cubins using `cuobjdump --dump-sass` or `nvdisasm` to check the emitted instructions. [CUDA binary utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/)
- **Occupancy and parallelism:** Calculate theoretical active warps per SM from block size, registers, shared memory, and architecture limits using the CUDA occupancy API or Nsight Compute `Occupancy`. Use achieved occupancy and the active, eligible, and issued warps from hardware counters to see what happened during execution. Interpret achieved occupancy with grid size, waves per SM, and effects from the final partial wave. [Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)
- **Instruction mix and compute utilization:** Use `ComputeWorkloadAnalysis` and `InstructionStats` for executed instructions, SM throughput, pipeline utilization, and the use of tensor, floating-point, integer, and load/store units. Use SASS to identify the operations the compiler emitted. Compute effective FLOP/s from a declared operation count and time, and identify datatype, accumulation precision, sparsity, and whether a fused multiply-add counts as two FLOPs. Identify hardware-counted operations separately when available. [Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)
- **Scheduler behavior, stalls, and divergence:** Use `SchedulerStats`, `WarpStateStats`, and source counters or PC sampling to locate issue starvation, memory dependency stalls, barriers, and branch divergence. Compare stall reasons with the rate of eligible and issued warps before attributing elapsed time to a specific stall. Associate source-level samples with the binary and line information used for the run. [Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)
- **Memory traffic and efficiency:** Use `MemoryWorkloadAnalysis` for device DRAM read/write bytes and throughput, L2 and L1/TEX traffic and hit rates, global memory sectors per request, shared-memory bank conflicts, and local-memory traffic associated with spills. Inspect atomics or reductions when they dominate a memory path. Record whether a metric counts bytes, sectors, or requests and which memory level it covers. Compute effective bandwidth from logical bytes divided by measured time. Compute physical bandwidth from counter bytes at a declared memory level divided by time. [Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)
- **Roofline and arithmetic intensity:** Divide counted work by bytes transferred at the selected memory level for arithmetic intensity, and divide work by kernel time for achieved performance. Use matching precision, clocks, and full-GPU or MIG resources for the ceilings. Mark estimates based on logical input/output bytes as such. A DRAM roofline derived from measured traffic needs DRAM counters. [Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)

## Memory footprint, telemetry, and correctness

- **Allocation footprint:** Sample baseline and peak allocated and reserved bytes using PyTorch allocator APIs. Allocated bytes describe live PyTorch allocations. Reserved bytes include memory managed by the allocator for reuse. For allocation lifetimes and fragmentation, use PyTorch's memory history and snapshots. For process or device memory outside PyTorch, use framework-independent telemetry where available and record whether it covers the process, MIG device, or board. [PyTorch CUDA memory usage](https://docs.pytorch.org/docs/stable/torch_cuda_memory)
- **Power, energy, clocks, and thermal state:** Sample temperature, power, utilization, clocks, and throttling indicators via NVML, `nvidia-smi`, or DCGM. Use a supported cumulative energy counter or integrate samples over a sustained interval to estimate joules. State the sampling interval, device scope, and any idle subtraction. Whole-board power on a shared MIG GPU cannot be attributed to an individual kernel or slice from that reading. [NVIDIA System Management Interface](https://docs.nvidia.com/deploy/nvidia-smi/) · [DCGM profiling guide](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/profiling.html)
- **Correctness and safety checks:** Compare outputs to a reference with declared tolerances and record the inputs, dtype, error summary, and pass/fail. Use Compute Sanitizer `memcheck` for memory-access errors, `racecheck` for shared-memory access hazards, `initcheck` for uninitialized memory reads within its supported scope, and `synccheck` for invalid synchronization. Log scope and findings separately from performance data. [Compute Sanitizer guide](https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/) · [Harness axioms](axioms.md)

## MIG and distributed execution

- **MIG capacity and isolation:** Record the GPU model, MIG profile, runtime-visible memory and SM count, GPU Instance and Compute Instance IDs when available, and evidence of whether the Compute Instance occupies its whole parent. A Compute Instance that occupies its whole GPU Instance avoids sibling sharing of that instance's memory resources. Sibling Compute Instances can share memory-system resources, making counters for shared units unavailable in Nsight Compute. Driver permissions are an independent restriction, and device-level clocks apply at the board level. To study interference, compare controlled runs across declared co-location conditions. [MIG device naming](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/mig-device-names.html) · [Nsight Compute MIG profiling](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)
- **Transfer paths and topology:** Record device and NUMA placement, CPU affinity, PCIe/NVLink paths, and peer access using `nvidia-smi topo -m`, NVML, and CUDA peer queries. Use `nvbandwidth` for host/device and supported peer copy bandwidth. Measure latency over small messages separately. Report direction, message size, pinned host memory, copy method, concurrency, and accessible peers. Use supported DCGM or device fields for live link traffic. [NVIDIA nvbandwidth](https://github.com/NVIDIA/nvbandwidth) · [DCGM profiling guide](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/profiling.html)
- **Collective latency and bandwidth:** Run the matching `nccl-tests` benchmark for all-reduce, all-gather, reduce-scatter, all-to-all, or another operation. Record rank placement, payload definition and size, datatype, in-place vs. out-of-place execution, validation, and warm-up count. Capture algorithm bandwidth and NCCL's operation-specific bus bandwidth separately. Use NCCL logs to identify the selected transport and available algorithm/protocol details. Use Nsight Systems NCCL tracing or the NCCL profiler plugin for per-rank timing. [nccl-tests metric definitions](https://github.com/NVIDIA/nccl-tests/blob/master/doc/PERFORMANCE.md) · [Nsight Systems guide](https://docs.nvidia.com/nsight-systems/UserGuide/)
- **Overlap, synchronization, and stragglers:** Trace computation and communication streams on each rank using Nsight Systems and consistent NVTX phase labels. Within a common time window, form the union of compute intervals and the union of communication intervals. Divide the duration of their intersection by the communication duration if reporting the fraction of communication that overlaps compute. Compare waits, rank spread, and the critical path alongside overlap. Align or correlate ranks before comparing timestamps across nodes. [Nsight Systems guide](https://docs.nvidia.com/nsight-systems/UserGuide/)
- **Network transport and scaling:** Correlate NCCL transport logs and rank timelines with scoped NIC or RDMA port counter deltas for traffic, errors, or retransmits when exposed by the fabric. Record interface, traffic direction, duration, and sharing scope. For strong scaling, hold the total workload fixed and report speedup `T1 / TN` and efficiency `T1 / (N × TN)`; for weak scaling, hold the work per rank fixed and report `T1 / TN` with the resulting total workload and throughput. [NVIDIA distributed benchmarking guide](https://docs.nvidia.com/multi-node-nvlink-systems/multi-node-tuning-guide/measuring-performance.html)

## Collection in the harness

1. **Baseline every candidate.** Record validation status, warm current-stream callable timing, the PyTorch allocator baseline and peaks, and the execution environment. The existing worker supports these measurements and can check correctness when the task provides a reference. Preserve raw samples and compare candidate and reference with the same input, resource allocation, and timing boundaries. [Worker measurement code](../../compute/src/kernel_compute/worker/measure.py) · [CLI validation](compute-cli-validation.md)
2. **Trace representative runs when diagnosing performance.** Capture kernel and transfer intervals, CPU dispatch and waits, framework phases, and collectives as applicable. Check that the expected GPU activities appear before accepting the trace. Export the raw report or trace, plus a small summary of the relevant ranges. [Nsight Systems guide](https://docs.nvidia.com/nsight-systems/UserGuide/)
3. **Collect targeted counters after a successful permission probe.** Choose the kernel and the smallest group of metrics that answers the question. Record replay mode and passes, kernel filters, clock and cache control, and architecture-specific metric names. Profile communication-dependent workloads only with a collection mode appropriate to concurrent execution. [Nsight Compute CLI](https://docs.nvidia.com/nsight-compute/NsightComputeCli/) · [Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)
4. **Record each measurement with its provenance.** Include value, unit, metric source and version, scope, sample count or interval, and collection conditions. At run level capture hardware, topology, driver, toolkit, input, dtype, launch configuration, clocks or power policy when relevant, and software revisions. Use explicit statuses such as unavailable, unsupported, permission denied, and not collected. Store zero only for a successful measurement with value zero.

### Waterloo starting point

- **Verified:** CUDA Events, Nsight Systems GPU software tracing, Compute Sanitizer `memcheck`, and compiler/SASS inspection worked on the tested full GPU and MIG slice. Host/device `nvbandwidth` worked on both, with `--disableAffinity` on MIG. Standalone two-node NCCL all-reduce and per-rank NCCL tracing worked over TCP.
- **Restricted or unverified:** Nsight Compute live collections failed with `ERR_NVGPUCTRPERM` on both allocations. Nsight Systems CPU sampling checks failed. DCGM basic telemetry worked on the full GPU, while its host engine required root on MIG. Same-node peer bandwidth and RDMA measurements remain unverified.
- **Provider capability is specific to the tested allocation.** The Modal T4 and Baseten A10G probes both captured CUDA traces. Modal collected an SM cycle counter with clock locking disabled. Baseten received a counter-permission error with the same clock setting. Recheck capabilities after changing GPU, driver, runtime, or provider profile. [Waterloo investigation](compute/uwaterloo-datasci.md) · [Modal investigation](compute/modal.md) · [Baseten investigation](compute/baseten.md)
