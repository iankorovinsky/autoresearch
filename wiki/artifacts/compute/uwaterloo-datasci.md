# University of Waterloo Data Science Cluster compute provider

Live observations from November 21, 2026 (America/Toronto). The initial inventory and implementation tests were followed by MIG and profiling probes around 22:00–22:14 local time. These results describe the tested accounts, allocations, and software versions. See the [cluster inventory](../datasci-gpu-investigation.md) and [compute CLI validation report](../compute-cli-validation.md) for the earlier evidence.

## Provider integration

- The existing `kcompute` provider ID is `waterloo-datasci`. It connects over SSH to `datasci-gpu.cs.uwaterloo.ca` with strict host-key checking. Slurm provides the durable job queue. The default profile uses partition `ALL`, node `gpu-8-vm`, and CUDA at `/usr/local/cuda-13.2`. The provider supports submission, status, logs, cancellation, and result retrieval. [Configuration and usage](../../../compute/README.md) · [Waterloo adapter](../../../compute/src/kernel_compute/providers/waterloo_datasci.py)
- The adapter requests one resource with `--gres=gpu:1`. Tasks default to `mig = "forbid"`, and the worker checks the actual allocation. The adapter rejects `mig = "require"` because it has no MIG profile selector. The measured protocol is `cuda-event-warm-v1`, which times the workload callable on its current stream after warm-up. The profiling and communications tools below were exercised in separate Slurm jobs. [Task and provider models](../../../compute/src/kernel_compute/models.py) · [Worker device checks](../../../compute/src/kernel_compute/worker/main.py)
- The validated default environment used driver `595.58.03`, CUDA Toolkit `13.2.86`, PyTorch `2.9.1+cu130`, and Triton `3.5.1`. Earlier end-to-end CLI tests exercised CUDA compilation and execution, output validation, result retrieval, cancellation, and submission recovery. [Compute CLI live tests](../compute-cli-validation.md#verification)

## Allocation and MIG layout

- **`gpu-8-vm` and `gpu-1-vm`** each provided a full NVIDIA RTX PRO 6000 Blackwell Max-Q Workstation Edition with MIG disabled. The initial inventory reported 97,887 MiB. The default Toolkit on `gpu-1-vm` was 13.3.73, so account for the compiler when comparing runs across nodes. [Earlier GPU and CUDA inventory](../datasci-gpu-investigation.md#gpu-and-cuda-configuration)
- **`gpu-6-vm`** returned one `2g.48gb` device from the same physical GPU model for a one-resource job. Jobs `8127` and `8128` saw GPU Instance 2, Compute Instance 0, 94 streaming multiprocessors, and 48,512 MiB of CUDA-visible memory. NVIDIA's device naming indicates that the Compute Instance uses the full compute capacity of its parent GPU Instance. For this GPU model, that profile provides half the physical card's compute and memory. [MIG naming](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/mig-device-names.html) · [RTX PRO 6000 profiles](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/supported-mig-profiles.html#rtx-pro-6000-blackwell-mig-profiles)
- Slurm exposed two GPU resources on `gpu-6-vm`. The second resource was occupied during inspection, and `nvidia-smi mig -lgi` and `-lci` returned insufficient permissions. The evidence covers the tested allocation. Nodes `gpu-2-vm` through `gpu-5-vm` had no available GPU resource at the initial inspection, and their MIG layouts remain unverified. [Earlier scheduler snapshot](../datasci-gpu-investigation.md#live-availability-snapshot)

## Live tool results

### Single GPU and MIG

- **CUDA Events and compiler tools** worked on both `gpu-8-vm` and `gpu-6-vm`. A CUDA kernel produced the expected output, CUDA Events returned an elapsed time, and `nvcc`, `ptxas`, `cuobjdump`, and `nvdisasm` compiled or inspected the GPU code. Jobs `8130` and `8131`.
- **Compute Sanitizer 2026.1.1** ran `memcheck` on both allocations. The valid kernel reported zero errors. A control kernel with an intentional out-of-bounds global write was flagged with a source line. Jobs `8130` and `8131`. [Compute Sanitizer guide](https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/)
- **Nsight Systems 2025.6.3** recorded CUDA kernels and memory copies on both allocations with `--trace=cuda-sw,nvtx --sample=none --cpuctxsw=none`. `nsys stats` produced GPU kernel and memory summaries. The environment check failed both process-tree and system-wide CPU sampling. Jobs `8130` and `8131`. [Nsight Systems guide](https://docs.nvidia.com/nsight-systems/UserGuide/)
- **Nsight Compute 2026.1.1** can show its version and list sections. The live metric query printed `ERR_NVGPUCTRPERM` despite returning exit status zero. Collection of `LaunchStats`, `launch__registers_per_thread`, `gpu__time_duration.sum`, `dram__bytes_read.sum`, and `sm__inst_executed.sum` failed with the same error on both allocations. Both nodes reported `RmProfilingAdminOnly=1`. Jobs `8129`, `8135`, and `8136`. [NVIDIA counter permissions](https://developer.nvidia.com/nvidia-development-tools-solutions-ERR_NVGPUCTRPERM-permission-issue-performance-counters)
- **NVML via `nvidia-smi`** reported device identity and board temperature, power, and clocks on both nodes. GPU and memory utilization were available on the full GPU and returned `N/A` in MIG mode. Jobs `8130` and `8131`.
- **DCGM 4.7.1** ran from user space with a private Unix socket on `gpu-8-vm`. Discovery and `dcgmi dmon` returned temperature, power, SM clock, and GPU utilization. SM activity and PCIe transmit profiling fields returned `N/A`. On `gpu-6-vm`, the host engine explicitly required root in MIG mode and failed initialization. Jobs `8140` and `8141`. [DCGM guide](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/getting-started.html)
- **`nvbandwidth` 0.11.0** completed copy-engine transfers with 16 MiB buffers. Host-to-device and device-to-host results were 57.58 and 57.21 GB/s on the full GPU, and 57.57 and 56.96 GB/s on MIG. The MIG run needed `--disableAffinity` to avoid an NVML UUID lookup failure. These short runs establish functionality. Jobs `8140`–`8142`. [NVIDIA nvbandwidth](https://github.com/NVIDIA/nvbandwidth/tree/v0.11.0)

### Communication and topology

- **PyTorch NCCL and standalone `nccl-tests` worked across nodes** with two full GPUs (`gpu-1-vm` and `gpu-8-vm`) and with one full GPU plus the MIG slice (`gpu-8-vm` and `gpu-6-vm`). Each rank had one CUDA device. NCCL 2.27.7 selected sockets in both configurations. The PyTorch probe validated a 1 MiB FP32 all-reduce. The standalone `all_reduce_perf` from `nccl-tests` 2.16.4 with MPICH 5.0.2 validated 64 KiB through 8 MiB with zero errors. The suite reported mean bus bandwidth of 0.578 GB/s for full/full and 0.513 GB/s for MIG/full. These are single smoke runs over the tested sizes. Jobs `8132`, `8133`, `8143`, and `8144`. [NVIDIA nccl-tests](https://github.com/NVIDIA/nccl-tests/tree/v2.16.4)
- **NCCL tracing worked with Nsight Systems** on the mixed allocation. With `--trace=cuda-sw,nvtx,nccl`, Nsight Systems loaded its NCCL profiler plugin and recorded the all-reduce kernel on both ranks. Job `8134`. [Nsight Systems guide](https://docs.nvidia.com/nsight-systems/UserGuide/)
- **Same-node P2P bandwidth remains unmeasured.** The tested single-node jobs each exposed one CUDA device, and `nvbandwidth` found no accessible peer pair. `nvidia-smi nvlink -s` reported no NVLink support on `gpu-8-vm` and unavailable queries in MIG mode on `gpu-6-vm`. The tested allocations exposed no InfiniBand devices. The successful TCP runs provide the verified multi-node path.

## Permissions and provider follow-up

1. **GPU performance counters.** Request an admin-approved way for SE390 Slurm jobs to collect NVIDIA counters on one isolated full-GPU node or profiling VM. On the tested driver branch, NVIDIA documents Linux `CAP_PERFMON` as one option, subject to execution-mode caveats. If direct access is unavailable, request an administrator-run probe and its `.ncu-rep` report. Verify access from inside a scheduled job with a small SM or DRAM counter collection and check the output for permission errors as well as the exit status. [NVIDIA counter permissions](https://developer.nvidia.com/nvidia-development-tools-solutions-ERR_NVGPUCTRPERM-permission-issue-performance-counters)
2. **MIG inventory and telemetry.** If the project needs node-wide confirmation, ask for the GI/CI layout or an administrator-run `nvidia-smi mig -lgi` and `-lci` on `gpu-6-vm`. If per-instance telemetry is needed, ask for read-only data for the allocated MIG device through an admin-managed DCGM service. [DCGM guide](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/getting-started.html)
3. **Interconnect testing.** If the workload requires it, request two peer-accessible physical GPUs on one Slurm node for same-node measurements, or access to an RDMA-capable partition for fabric measurements. The existing adapter's one-device contract would need separate multi-rank support to integrate the verified direct Slurm NCCL workflow.

The current default provider is suitable for single-GPU CUDA-event benchmarking. If the harness adds Nsight Systems tracing, verify and report it as a separate measurement mode. Before advertising MIG scheduling, verify how Slurm selects the requested profile and record the actual MIG profile and device memory alongside results. Track unavailable profiling metrics explicitly.

The follow-up jobs used the regular SE390 account. DCGM, `nvbandwidth`, and standalone `nccl-tests` were built or unpacked in temporary user space. The test jobs finished and the temporary cluster build directory was removed. Use the job IDs above to look up accounting records where available. [Waterloo Slurm documentation](https://datasci-gpu.cs.uwaterloo.ca/slurm.html)
