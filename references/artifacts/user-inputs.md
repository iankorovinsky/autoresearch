# Possible User Inputs

This taxonomy describes possible inputs to an automated GPU kernel research harness. It is a design exploration, not a list of currently supported interfaces.

Inputs that describe the desired computation are distinct from inputs that constrain how it should run. A request can combine several of the following sources.

## Example submission format

The final column shows a proposed user-facing submission: a natural-language message plus any attached files. These examples do not imply an implemented upload interface, command syntax, or mandatory schema. All attachment names are illustrative; the files are not included in this document. A repository path or accessible link can replace an attachment when it identifies the same material.

An idea can arrive as text alone. When a request relies on code, a paper, a callable library, or evaluation data, the corresponding material must be accessible before the harness can use it. Missing details become clarification questions rather than silently chosen correctness requirements.

## Accompanying constraints

Across all input types, the harness may also receive target hardware, representative shapes, data types, layouts, accuracy requirements, latency or memory budgets, and integration constraints. These accompany a request rather than replace a definition of the computation.

## Request intent

A useful distinction is whether the user wants to:

- **Implement a known computation.** Establish its contract and generate an implementation.
- **Improve an existing implementation.** Preserve the required behavior while optimizing, repairing, or porting it.
- **Discover a new computation.** Explore candidate algorithms, define a correctness contract for each, and evaluate their research objectives empirically.

This distinction determines how much specification work must happen before kernel generation.

## Coverage review

The following additional requests are feasible in principle but already fit the categories above, so they do not need separate input rows. This classification does not assert that the current harness implements them.

- **Port a kernel to another GPU or language:** existing kernel source, or a callable library, plus target hardware and integration constraints.
- **Fuse several operations:** a model/computation graph or reference implementation plus a specified fusion boundary.
- **Repair a correctness bug:** existing kernel source plus a failing test or execution trace and an independently established behavioral contract. The buggy output is not the reference.
- **Generate a backward or gradient kernel:** a forward reference implementation or equation plus a differentiation request. The derivative convention, nondifferentiable cases, and output interface must be specified.
- **Introduce quantization or approximate arithmetic:** an equation, reference implementation, or research objective plus explicit rounding, saturation, error, and quality requirements.
- **Implement an operator from API documentation or a standard:** a documented contract expressed through equations, properties, and invariants. Unlike the callable-library case, no executable oracle is implied.
- **Optimize a shape-specialized kernel:** any computational input plus a restricted set of shapes, layouts, and hardware constraints. Specialization changes the accepted input domain, not the source category.
- **Resume an earlier experiment:** a combination of existing source, tests, profiles, and experiment constraints. Prior results are evidence to reproduce, not a new definition of the computation.

No additional top-level categories were needed for these cases. A proposed new category should supply a materially different source of behavioral requirements or evidence, rather than only a different optimization goal, file format, or target device.
